Exact versions, paths, ownership and checksums for the environment this fix was developed and verified against. Use it to confirm your NAS matches before installing, and to audit what changed afterwards.

## Runtime dependencies

The replacement links only against libraries DSM already ships. Everything else is statically bundled.

| Shared object | Present on DSM 7.3.2 |
|---|---|
| `libcurl.so.4` | yes |
| `libssl.so.3` | yes |
| `libcrypto.so.3` | yes |
| `libm.so.6` | yes |
| `libc.so.6` (glibc 2.36) | yes |
| `ld-linux-x86-64.so.2` | yes |

Statically bundled instead of linked: libevent, libdeflate, libpsl, libb64, dht, libutp, libnatpmp, miniupnpc, plus `libstdc++` and `libgcc`.

Linking against the system copies fails at startup, because Debian 12 ships `libevent-2.1.so.7` while DSM has `libevent-2.1.so.6`, and DSM has no `libdeflate.so.0` or `libpsl.so.5` at all.

## Patches

Applied in order by [build/build-in-container.sh](build/build-in-container.sh), which now fails the build when the directory is absent rather than emitting an unpatched daemon.

### 0001-honor-downloadstation-task-id.patch

| File | Lines changed | Purpose |
|---|---|---|
| `libtransmission/torrents.h` | +2 | Declare `tr_torrents_set_pending_id` |
| `libtransmission/torrents.cc` | +39 -2 | Place a torrent at a caller-supplied id, falling back to sequential |
| `libtransmission/rpcimpl.cc` | +6 | Read DownloadStation's `task-id` argument in `torrent-add` |

### 0002-report-added-for-downloadstation-duplicate.patch

| File | Lines changed | Purpose |
|---|---|---|
| `libtransmission/torrents.h` | +2 | Declare the peek and clear accessors for the pending id |
| `libtransmission/torrents.cc` | +10 | Define them |
| `libtransmission/rpcimpl.cc` | +13 | Report `torrent-added` when a duplicate already carries the requested `task-id`, and clear the pending id on every add attempt |

Both are plain unified diffs against the upstream `4.1.1` tarball, applied with `patch -p1`. The second applies on top of the first and depends on it, since it extends the pending-id mechanism the first introduces.

## Ownership and permissions

| Object | Owner | Mode | Note |
|---|---|---|---|
| Vendor `transmissiond` | `DownloadStation:DownloadStation` | `755` | As shipped |
| Installed `transmissiond` | `DownloadStation:DownloadStation` | `2755` | setgid, required so the socket gets the right group |
| `transmissiond.stock` | `DownloadStation:DownloadStation` | `755` | Restored verbatim by `uninstall.sh` |
| `/tmp/synodl_transmission.sock` | `root:DownloadStation` | `srwxrwx---` (`0770`) | Group must be `DownloadStation` or the scheduler cannot connect |

The setgid bit is load-bearing. Without it the daemon's effective group is `root`, the socket is created `root:root`, and `synodlscheduler` (which runs as the `DownloadStation` user) fails to open it.

`/tmp` is mounted `noexec` on DSM. A binary staged there cannot be executed, so the installer copies it into the package directory before validating it.

## Shutdown timing

Measured on the verified environment, with a library of 21 torrents totalling roughly 30 TB declared and 17 TB present on disk.

| Quantity | Value |
|---|---|
| systemd default `TimeoutStopSec` | 90 s |
| Observed time to write every resume file after `SIGTERM` | about 83 s |
| Margin against the default | about 7 s |
| Installed `TimeoutStopSec` | 300 s |
| Largest single torrent | 6.58 TB, 392,361 pieces, 50 MB resume file |
| Process state after the save completes | `S`, blocked in `futex_wait_queue_me`, never exits |

The daemon does not exit on its own once the save is done, so every stop ends in `SIGKILL` regardless of the timeout. The value chosen therefore only has to be long enough to cover the save. Reads of `/proc/<pid>/task/*/wchan` during a stop show the saving thread in `D` state on `wait_on_page_bit_killable`, which is why the duration tracks disk throughput rather than CPU time.

### Observed across a real power-off

The drop-in was exercised by an unplanned full power-off, which is a stronger test than `systemctl stop` because DSM drives the shutdown on its own schedule.

| Observation | Value |
|---|---|
| `synopoweroff` logged | 13:26:51 |
| Every resume file's mtime | 13:26 |
| Largest resume file written | 12,023,823 bytes, the 1.68 TB torrent |
| Volume unmount began | 13:27:26 |
| Drop-in after the cold boot | present, `TimeoutStopUSec=5min` |
| Boot task after the cold boot | ran, `exit_code 0` |

Every torrent's state was written before the volume was unmounted, including the bitfield of the torrent that previous cycles had truncated. On the same hardware without the drop-in, this is the point at which progress was lost and a re-download began.

To measure it on another system, stop the unit and watch the resume directory rather than the unit state:

```sh
sudo systemctl stop pkg-DownloadStation-transmissiond.service &
watch -n 5 'ls -la --time-style=+%H:%M:%S /var/services/download/transmissiond/resume/'
```

The save is complete once the newest mtime stops advancing. Anything after that is the hang, not work.

## Verifying an installation

```sh
sudo ./scripts/verify.sh
```

A healthy result reports the active daemon as 4.1.1, `patch state: ACTIVE`, and an RPC probe of `RESPONSE HTTP/1.1 409 Conflict`. The 409 is correct: it is Transmission requesting a session id, which proves the request reached the handler and got an answer. The broken daemon returns `NO_RESPONSE timeout` instead.

Recorded result from the verified environment:

```
active daemon:  transmission-daemon 4.1.1 (56442e2929)
active md5:     ff85cb20374b4f28f00e59d7d15f4ffc
stock backup:   transmission-daemon 4.0.5 (82ea3bbe46)
stock md5:      b9563c971fab98399f34226abe528a0f
patch state:    ACTIVE
shutdown grace:  300s
rpc probe:      RESPONSE HTTP/1.1 409 Conflict
verdict:        PASS
```

`shutdown grace: MISSING` means the drop-in is absent and the unit is back on the 90 second default. The daemon still answers RPC in that state, so the probe passes and the fault stays hidden until the next restart. Run `reapply.sh` to restore it.

The end-to-end check is a real torrent. On the verified environment, an Ubuntu 24.04.4 server ISO added through DownloadStation reached 16% at 7.5 MB/s with 200 connected peers, with DownloadStation reporting the correct total size of 3,405,469,696 bytes and a `.part` file growing in the destination folder. Before the fix the same torrent produced `Failed to add torrent` and never wrote a byte.
